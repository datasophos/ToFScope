# Multi-Peak 3D Mapping Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox syntax for tracking. Implementation requires a separate user instruction; this plan is a proposed design.

**Goal:** Explore several ion signals in tiled 3D views or an overlay with independent colormaps.

**Architecture:** Build volume layers from shared signal recipes and a common acquisition-coordinate preview grid. Keep Plotly for the first deliverable, separate numerical layer data from display style, and preserve the existing single-signal fallback.

**Tech Stack:** NumPy, existing HDF5 reader, Plotly WebGL, AnyWidget, unittest, Playwright

**Spec:** [Roadmap design brief, section 1](../specs/2026-10-16-roadmap-design.md).

## Global Constraints

- Keep Marimo + AnyWidget + Plotly; do not introduce Panel.
- Treat frame limits as zero-based and inclusive.
- Do not change source HDF5 files except through explicit write-back.
- Preserve existing shared ROI, All depths, maximize/restore, and offline operation.
- Scientific transforms must not silently change analysis intensities.

## Dependencies and file boundaries

Requires the disjoint-window plan's `SignalRecipe` and `read_signal`; configured file browsing and depth calibration are not required. Add `volume_layers.py` for geometry/data/style models and `web/volume_layers.js` for controls/camera synchronization. Keep plot construction in `plots.py` with a small API change.

## Review Focus

- Signals with different frame origins/coverage must align by acquisition coordinates and retain missing regions (Task 1).
- One-layer, all-zero and one-voxel-thick selections must remain usable (Tasks 1, 2).
- Adding layers must not multiply preview memory without a total budget (Tasks 1, 2).
- Linked-camera events must not loop or erase deliberately independent tile cameras (Task 3).
- Transparency/color scaling can hide a layer; enabled/disabled state and its intensity scale must stay explicit (Tasks 2, 3).

### Task 1: Produce aligned, bounded layer previews

**Files:** Create `volume_layers.py`, `tests/test_volume_layers.py`; modify `explorer.py` only to expose reusable block reduction helpers.

**Interfaces:** `VolumeLayer(id: str, recipe: SignalRecipe, visible: bool, colorscale: str, opacity: float, percentile: float)`; `PreviewGrid` contains absolute X/Y/Z block centers and edges; `VolumePreview` contains values, valid coverage and intensity scale. `build_layer_previews(path, layers, roi, frames, *, quality: str, voxel_budget: int=500_000) -> list[VolumePreview]`.

- [ ] Write synthetic tests for two identical physical features in signals beginning at frames 10 and 12. Overlapping coverage must align at the same absolute Z; uncovered blocks remain masked. Test ROI offsets and pixel/FOV units against the existing preview helper.
- [ ] Test constant signals, all-zero layers, partial edge blocks and a thin one-frame slab. Means must equal original-data valid-voxel means; missing values must not be padded with zero. A total 500,000-voxel budget must hold across all enabled layers, with identical coordinate grids for an overlay.
- [ ] Run `uv run python -m unittest discover -s tests -p 'test_volume_layers.py' -v`; verify failure, then implement common block edges, per-layer validity-aware reduction and metadata. Exclude invisible layers from work, and retain original intensities separately from optional display log transforms.
- [ ] Cache by source identity, recipe derivation, ROI, frame window and reduction grid. Color/opacity/camera changes must not reload or reconstruct raw volumes. Record actual preview shapes and coverage for the UI.
- [ ] Run tests and compare a one-layer result with current `volume_plot` on the example. Commit: `Build aligned multi-signal volume previews.`

### Task 2: Render tiled and overlaid volumes

**Files:** Modify `plots.py`, `workspace.py`; create `tests/test_volume_figures.py`.

**Interfaces:** `overlay_volume_plot(previews, layer_styles, *, scale_mode: str='independent', stretch: float=1.2) -> go.Figure`; `tiled_volume_plot(previews, layer_styles, *, stretch: float=1.2) -> go.Figure` accepts at most four visible-page previews; the controller pages additional configured layers without losing styles/cameras. Single-layer `volume_plot` remains a supported adapter. `scale_mode='shared'` uses one numerical range in the same intensity/display units, not per-layer normalization.

- [ ] Write figure tests for trace colorscale/opacity/visibility, absolute coordinates, scene assignment per tile, masked gaps, independent/shared scale bounds and unchanged intensity values. One-frame selections must use a visible point/surface fallback instead of a degenerate volume.
- [ ] Run `uv run python -m unittest discover -s tests -p 'test_volume_figures.py' -v`; verify failure, then render overlays as multiple traces in one scene and tiles as separate scenes. Label each signal, mass intervals, frame coverage and scale; suppress overlapping colorbars in favor of a selected-layer scale display.
- [ ] Add controller events `volume_layer_add {recipe_id}`, `volume_layer_remove {id}`, `volume_layer_style {id,...}`, `volume_layout {mode}`, `volume_scale {mode}`. Resolve only registered recipes from the current acquisition; validate style values/colormaps on the server.
- [ ] Benchmark one and three layers on the actual AlTiPt file and client Chrome: record preparation time, payload size and rotation behavior. Proposed acceptance targets for three stored Fast layers on the client machine are preview-ready within 10 seconds, at most 32 MiB total encoded preview payload, and 95th-percentile drag-to-render latency below 200 ms over 30 interactions; keep raw reconstruction time separate. Review these proposed targets with the client before execution. If overlays are unusable even at the capped Fast preview, keep tiled views shippable and record a separate renderer decision with measured evidence; do not silently change renderer or claim overlay acceptance.
- [ ] Run numerical/figure tests. Commit: `Render tiled and overlaid ion volumes.`

### Task 3: Add layer controls and linked cameras

**Files:** Create `web/volume_layers.js`, `scripts/check_multi_volume.py`; modify `web/workspace.js`, `web/workspace.css`, `workspace.py`, `README.md`.

**Interfaces:** Component `mountVolumeLayers(root, {send, getPlot}) -> {update, dispose}` manages registered IDs, layout and camera-link mode. Camera changes are view state; changes to recipe/ROI/depth invalidate previews. Use a guarded Plotly relayout handler and unsubscribe on dispose.

- [ ] Write a failing browser scenario adding three stored/custom signals, assigning distinct colormaps, switching tiles/overlay, hiding/removing a layer, changing ROI/depth, and maximizing/restoring the 3D display. Each tile/legend must name the correct recipe and show its actual preview coverage.
- [ ] Test an empty layer set, all-zero layer, single-frame layer, partial coverage and more layers than the initial viewport can show. The layer list scrolls; tiles page four scenes at a time to bound WebGL contexts. Test page changes preserve camera/style state and release off-page scene resources. Overlays reduce resolution under the total budget rather than enforcing a hidden fixed count limit.
- [ ] Implement per-layer visibility, colorscale, opacity and threshold with tiled/overlay and linked-camera toggles. Include a solo action so users can inspect an obscured overlay component. Keep profile relative-scaling controls separate.
- [ ] Run `uv run python scripts/check_multi_volume.py`, existing volume-context/display/all-depth checks, and layer tests. Verify camera-link relayout events do not recursively emit, independent cameras stay independent, and source changes preserve sensible camera state.
- [ ] Document preview limits/occlusion and commit: `Control and compare multiple 3D ion layers.`

## Acceptance

At least three independently styled signals can be tiled and overlaid on the example data with correct coordinates, bounded previews, explicit identities and working shared ROI/depth/maximize interactions. The actual-browser benchmark must pass before declaring overlays complete.
